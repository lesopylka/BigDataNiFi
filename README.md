## Данные и модель

В [data](data) находятся 10 CSV по 1000 строк. Переносы строк внутри описаний товаров обрабатываются CSV-парсером.

Одна строка исходного файла считается одной продажей. Номер `id` повторяется между файлами. Ключ продажи состоит из имени файла и номера строки `id`. Поля `sale_customer_id`, `sale_seller_id` и `sale_product_id` не используются как уникальные ключи справочников.

Сумма продажи берется из `sale_total_price`. Она не заменяется произведением цены на количество, так как эти значения в учебных данных расходятся.

Контрольные значения находятся в [expected.json](expected.json).

| Показатель | Значение |
|---|---:|
| Продажи | 10000 |
| Количество товара | 54623 |
| Сумма продаж | 2529852.12 |

## Витрины

Каждая витрина содержит несколько показателей. Поле `metric` определяет показатель, `entity` определяет объект, `period` содержит период, `value` содержит значение. В ClickHouse это шесть отдельных таблиц. В NiFi это шесть SQL-представлений PostgreSQL.

| Витрина | Показатели |
|---|---|
| products | Топ-10 по количеству, выручка категорий, средний рейтинг, число отзывов |
| customers | Топ-10 по сумме покупок, уникальные email по странам, средний чек |
| time | Выручка по месяцам и годам, разница с предыдущим периодом, средний чек по месяцам |
| stores | Топ-5 по выручке, выручка городов и стран, средний чек |
| suppliers | Топ-5 по выручке, средняя наблюдаемая цена, выручка по странам |
| quality | Лучшие и худшие рейтинги, больше всего отзывов, корреляция рейтинга и количества |

Товары в сводных отчетах группируются по названию. Уникальные версии товара предварительно выделяются по всем характеристикам. Рейтинг усредняется по версиям, отзывы суммируются по версиям, а не по повторным продажам той же версии. Поле отзывов трактуется как число отзывов в каждой версии учебного товара.

Клиенты группируются по email, магазины и поставщики тоже по email. Средний чек считается по строкам продаж, так как отдельного номера заказа в CSV нет. Корреляция считается по товарам между средним рейтингом и суммарным проданным количеством. При отсутствии предыдущего периода изменение выручки равно NULL.

## Реализация

[Scripts/produce.py](Scripts/produce.py) отправляет CSV в Kafka по одной строке в JSON. [Scripts/setup_nifi.py](Scripts/setup_nifi.py) создает настоящий flow через REST API NiFi.

В группе `sales_pipeline` находятся `ConsumeKafka_2_6`, `PutDatabaseRecord`, `JsonTreeReader` и `DBCPConnectionPool`. Успешные записи завершаются. Ошибки `retry` возвращаются в очередь записи, `failure` остаются в очереди перед остановленным `LogAttribute` для разбора. Ошибочные записи автоматически не удаляются.

`PutDatabaseRecord` выполняет UPSERT по `sale_key`. Повторная доставка обновляет исходную строку, а не добавляет дубль. Данные PostgreSQL хранятся без агрегаций. [sql/02_views.sql](sql/02_views.sql) формирует отчеты как SQL-представления.

Поток сохраняется в томах NiFi. Скрипт настройки создает его один раз. При повторном запуске сообщает, что группа уже существует, и не создает дубликат. Незавершенную настройку нужно разобрать в UI перед повторным созданием.

## Запуск

Нужны Docker с Compose v2, интернет для загрузки образов и драйвера, минимум 8 ГБ свободной памяти.

```bash
cp .env.example .env
```

В `.env` нужно установить свой `MB_EMAIL` и пароль `MB_PASSWORD` длиной от 12 символов с цифрами и разным регистром. Файл с паролем не коммитится.

```bash
docker compose up -d --build
docker compose logs -f setup
```

После сообщения о создании потока открыть `http://localhost:8082/nifi` и проверить два работающих процессора. Затем отправить данные.

```bash
docker compose --profile send run --rm producer
docker compose run --rm producer python Scripts/verify.py
```

Контрольные SQL-запросы находятся в [Scripts/check.sql](Scripts/check.sql). В PostgreSQL на `localhost:5435` база, пользователь и пароль равны `postgres`.

## Metabase

После загрузки данных запустить создание дашборда.

```bash
docker compose --profile dashboards run --rm dashboards
```

[Scripts/setup_metabase.py](Scripts/setup_metabase.py) создает локального пользователя при первой настройке Metabase, подключение PostgreSQL и дашборд с 22 карточками. Если Metabase уже настроен, в `.env` нужны данные существующего администратора.

Открыть `http://localhost:3000`, войти с данными из `.env`, выбрать дашборд «Лабораторная работа 5». Повторный запуск не добавляет такой же дашборд. SQL карточек можно редактировать через «Открыть вопрос» и SQL-редактор. Для ручного подключения PostgreSQL использовать хост `postgres`, порт `5432`, базу и учетные данные `postgres`.

Проверить, что очередь failure пустая, количество строк равно 10000, суммы совпадают с `expected.json`, а все карточки выполняются без ошибок. После повторной отправки CSV количество строк должно остаться 10000.

## Проверки и ограничения

Проверены количество строк в каждом CSV, уникальность составного ключа и контрольные суммы. Для SQL витрин выполнен локальный расчет на полном наборе данных. Контейнерный запуск и связь всех сервисов требуют проверки команд выше. Успешный локальный SQL-расчет не заменяет интеграционный запуск.

Параметры баз в compose предназначены для локальной лабораторной работы. Сервисы привязаны к localhost. Разные работы можно запускать по отдельности. Инициализационные SQL выполняются только на пустом томе PostgreSQL.

Остановить сервисы с сохранением данных можно командой `docker compose down`. Команда `docker compose down -v` удаляет учебные базы, очереди и состояние сервисов. Для запуска с нуля после удаления томов повторить шаги из раздела запуска.
